Interview App · Documentation

API contract#

Base URL: http://127.0.0.1:8765 (local only). JSON in and out. Errors use FastAPI's shape: {"detail": "message"} with a 4xx/5xx status. Timestamps are ISO-8601 UTC strings.

Every agent-produced object carries a meta block describing how it was made:

{"trace_id": "trc_…", "provider": "ollama | claude | heuristic", "model": "qwen3:14b",
 "status": "ok | repaired | fallback | degraded", "attempts": 1, "latency_ms": 2140}

degraded means no language model was available and built-in rules produced the result.

Speech-to-text#

WS /api/stt/ws?mode=practice|meeting&meeting_id=&channel=me|them&offset=<seconds>#

  1. Server sends {"type": "ready", "engine", "model", "device"} — or {"type": "unavailable", "detail"} and closes (the client then falls back to the browser's speech recognition, mic only).
  2. Client streams binary frames: 16 kHz mono PCM16 little-endian, ~100-250 ms per frame.
  3. Server sends {"type": "partial", "channel", "text"} while you speak and {"type": "final", "channel", "text", "t0", "t1", "segment_id"} at each pause. In meeting mode, finals are saved as segments: channel me → speaker Me, them → Them.
  4. Client sends {"type": "stop"}; server flushes, sends remaining finals, then {"type": "done"} and closes.

POST /api/stt/transcribe (multipart file: webm/wav/ogg/mp3)#

→ {"text", "segments": [{"t0", "t1", "text"}], "duration_sec", "engine"}

Jobs: search and human-in-the-loop applications#

Every application passes a human approval gate. The app may fill a form in a visible browser, but it never clicks Submit. The user does. AI drafts only open-text answers, grounded in the CV. Legal and compensation questions are answered only from values the user typed (legal answers are remembered per country). Consent and voluntary self-identification (EEO) questions are never filled or stored: the user answers them in the form.

Search preferences#

  • GET /api/careers/preferences / PUT /api/careers/preferences (partial) → {titles: [str], keywords: [str], exclude_keywords: [str], locations: [str], remote: "any|remote_only|onsite_ok", seniority: [str], min_score: 0-100, max_results: 10-500, aggregators: {remotive: bool, arbeitnow: bool}}. Search and matches#

  • POST /api/careers/search {"refresh"?: bool} → {"job_id"}. The pipeline: plan → fetch from every enabled source in parallel → normalize and dedupe → score → AI rerank of the best → save. Job steps: plan, fetch, score, rerank, save.
  • GET /api/careers/matches?min_score=&recommendation=&q=&limit=50 → [Match] (best first; dismissed hidden)
  • GET /api/careers/postings/{id} → Posting plus description_text and questions (when the source exposes them)
  • POST /api/careers/postings/manual {"title", "company", "description_text", "url"?, "apply_url"?, "location"?} → Match (for a job found anywhere, e.g. LinkedIn: paste it in)
  • POST /api/careers/postings/{id}/dismiss → {"ok": true}
Posting = {id, source: "greenhouse|lever|ashby|smartrecruiters|remotive|arbeitnow|manual", source_label, company, title,
           location, remote: bool|null, workplace, department, employment_type, posted_at, url, apply_url, salary,
           description_snippet, attribution: str|null}       # e.g. "Source: Remotive" with a link back (their terms)
Match = {posting: Posting, score: 0-100, det_score, llm_score: int|null, recommendation: "apply|maybe|skip",
         reasons: [str], gaps: [str], red_flags: [str], application_id: str|null,
         meta: {components: {title, skills, location, seniority, keywords, recency, feedback?},
                skills_matched: [str], skills_missing: [str], reviewed_by: "model|rules", also_in: [location],
                rubric: {must_haves: [{requirement, status: "met|partial|missing", evidence, note}],
                         nice_to_haves: [...]}|null}}
# score = det_score, or 0.4*det_score + 0.6*llm_score when a model reviewed it. llm_score is computed in code from
# the rubric (met=1, partial=0.5), and a "met" whose CV quote can't be found in the CV is downgraded to "partial".
Question = {key, label, kind: "text|textarea|select|multiselect|file|boolean", required, options: [str],
            category: "profile|open_text|legal|demographic|compensation|consent|availability|file|other"}

Applications#

  • POST /api/careers/applications {"posting_id"} → 201 {"application": Application, "job_id"} (drafts the materials, then runs the truth check). If an application for that job already exists: 200 with it.
  • GET /api/careers/applications?status= → [{id, status, posting: {company, title, location, url}, score, created_at, updated_at, approved_at, submitted_at, follow_up_at}]
  • GET /api/careers/applications/{id} → Application
  • PUT /api/careers/applications/{id} {"materials"?: {summary?, cover_letter?, highlights?}, "answers"?: [{key, value}], "notes"?, "follow_up_at"?} → Application (edited text is re-checked). A select answer must match one of its options; a multi-select takes a list or "a; b" (stored as "a; b"). Consent and voluntary self-identification answers are ignored, because the user gives them in the form.
  • POST /api/careers/applications/{id}/regenerate → {"job_id"}
  • POST /api/careers/applications/{id}/truth/{issue_id}/ack → Application (the user confirms the claim is true)
  • POST /api/careers/applications/{id}/approve → Application or 409 {"detail", "blockers": [str]}
  • POST /api/careers/applications/{id}/fill → {"job_id"} (installed app only). Opens a visible browser, fills the form, uploads the CV, then stops before Submit. 400 for mode: "assist" sites; 409 if not approved, if it changed since approval, or if another application is being filled; 501 with setup steps if Playwright isn't installed. After the user submits, the confirmation page is detected and the status becomes submitted.
  • POST /api/careers/applications/{id}/submitted {"note"?} → Application (the user confirms they submitted)
  • POST /api/careers/applications/{id}/status {"status": "interviewing|offer|rejected|withdrawn"} → Application
  • POST /api/careers/applications/{id}/prep → {"target_id", "job_id"} (creates an interview-coach target from the posting and the CV)
  • DELETE /api/careers/applications/{id} → {"ok": true}
  • GET /api/careers/stats → {approved_today, daily_limit, by_status: {…}, sources_enabled, postings, last_search_at, last_search: {at, run_id, fetched, relevant, saved, reviewed, apply, titles, errors}|null, browser: {available, channel, busy, detail, setup?: [str]}}. postings is the number of matches the last search saved.
Application = {id, status: "preparing|needs_review|approved|filling|filled|submitted|interviewing|offer|rejected|withdrawn|failed",
               posting: Posting (+description_text), match: Match|null,
               materials: {summary, cover_letter, highlights: [str]},
               answers: [{key, label, kind, required, category, options, value, source: "profile|saved|ai|user|empty",
                          needs_input: bool, note}],
               truth: {ok, issues: [{id, field, text, problem, severity: "block|warn", acknowledged, source: "rules|ai"}], meta},
               checklist: [{key, label, ok, blocking: bool, detail}],   # only blocking items stop approval
               fill_report: {filled: [str], skipped: [str], needs_attention: [str], captcha: bool, email_code: bool,
                             login_required: bool, submit_button_found: bool, url, at}|null,

               mode: "fill|assist",            # fill = Greenhouse/Lever/Ashby/SmartRecruiters form; assist = copy answers
               warnings: [{kind: "ai_directive|ai_screening|duplicate|info", text, url?}],
               questions_origin: "board|standard",
               created_at, updated_at, approved_at, submitted_at}

Approval rules: editing materials or answers of an approved application moves it back to needs_review. At most careers.daily_application_limit (default 10) applications can be approved per day. Answers the user typed for legal, availability, compensation and other questions are saved to saved_answers on approval.
